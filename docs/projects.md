# Corion Capital — Trade Ledger

## 1. Mission
Build a locally runnable trade capture and tracking application in 10 minutes using FastAPI, React (Vite) and SQLite. Prioritize a correct end-to-end workflow, financial calculations, explicit assumptions and explainable code over completeness. The interview permits AI assistance but the human engineer must understand every decision.


## 3. Scope and priorities
| Priority | Deliverable |
|---|---|
| P0 | Import and inspect market data; instrument lookup and latest closes |
| P0 | Capture and persist valid draft trades; list today's trades; filter by fund |
| P0 | Correct consideration by instrument quotation convention; explicit side and broker |
| P1 | Price deviation warning; sequential status transitions and executed price |
| P2 | End-of-day CSV export; executed positions by fund and instrument |
| Deferred | Authentication, commissions, real broker connectivity, full audit trail, production deployment |

If time runs short, preserve the working P0 vertical slice. Do not start optional features while core integration is broken.

Use SQLite foreign keys and parameterized SQL. Keep dependencies minimal: FastAPI, Pydantic, sqlite3, React and Vite. No unnecessary ORM, state management framework or Docker.

## 6. Domain model and financial rules
Trade fields: id, trade_date, fund, instrument_id, side, qty, price, broker, status, executed_price (nullable). Consideration is derived, not independently editable. Use Decimal for calculations; persist decimal values as exact decimal strings (TEXT) where practical. API decimal fields are strings to avoid JSON floating-point ambiguity. Quantities and prices must be finite and positive. Side is BUY or SELL, explicitly selected. Consideration is unsigned; side determines position direction. No implicit FX conversion or cross-currency totals.

Funds: KESCON, FYNBAL, BAOGLB, PROINC.
Brokers: Kudu Securities, Impala Capital, Springbok Stockbrokers.
Hardcode these server-side for MVP and expose via API. Reject unknown values.

| Instrument convention | Consideration |
|---|---|
| JSE shares quoted in cents | qty × price / 100 (ZAR) |
| Shares quoted in currency units (e.g. USD) | qty × price |
| Bonds quoted per 100 nominal | nominal × price / 100 |
| ALSI future | contracts × points × 10 (assumed ZAR multiplier per brief) |
| Unknown convention | Reject calculation with an explicit explanation |

For bonds assume entered price is all-in for MVP; do not invent accrued interest. If source close is clean and trade price is all-in, suppress the comparison unless comparable bases are confirmed. Futures consideration is contract notional, not margin or cash settlement. Verify actual metadata before classifying; do not infer solely from instrument code. Use integer contracts for futures; fractional equity/nominal rules need desk confirmation. Round displayed money to two decimals, retain calculation precision until final rounding.

Status: DRAFT -> SENT -> EXECUTED -> DONE. New trades always DRAFT. No skipping or reversing. EXECUTED requires positive executed_price; DONE retains it. Effective consideration uses captured price before execution and executed price afterward. Preserve original captured price. SENT only records a manual status; no email is sent.

Price warning: provisional threshold strictly greater than 5% absolute deviation: abs(price - close) / close. Use most recent valid dated close on or before trade date, in comparable units. Missing/zero/noncomparable close produces an explicit unavailable warning, not a fake zero or rejection. Re-evaluate against executed price at execution if implemented. No look-ahead prices. Trade date defaults to South African local today; dates stored ISO YYYY-MM-DD.

## 7. Shared API contract (freeze before parallel implementation)
Base URL: `http://localhost:8000/api`. Vite: `http://localhost:5173`.

| Method | Route | Purpose |
|---|---|---|
| GET | /api/health | Database readiness |
| GET | /api/reference-data | Funds and brokers |
| GET | /api/instruments | Actual instruments with latest close metadata |
| GET | /api/trades?date=YYYY-MM-DD&fund=KESCON | List trades; date defaults to local today; fund optional |
| POST | /api/trades | Capture draft |
| PATCH | /api/trades/{id}/status | Advance status |
| GET | /api/trades/export?date=YYYY-MM-DD&fund=KESCON | Optional CSV |
| GET | /api/positions?fund=KESCON | Optional executed net quantities |

Reference data: `{ "funds": ["KESCON"], "brokers": ["Kudu Securities"] }` (example abbreviated; return all configured values).
Instrument list: array of `{id, code, name, asset_class, currency, quote_unit, last_close, last_close_date}`. IDs are integers unless actual data requires an explicitly communicated change. Close/date may be null. Preserve actual source metadata; normalize calculation conventions internally.

Create request example (instrument ID illustrative; select real ID from API):
```json
{"trade_date":"2026-11-26","fund":"KESCON","instrument_id":1,"side":"BUY","qty":"100","price":"2500","broker":"Kudu Securities"}
```
Trade response: all create fields plus `id`, `instrument_code`, `currency`, `status`, `executed_price`, `consideration`, `last_close`, `last_close_date`, `price_deviation_pct`, `warning` (nullable). Decimal fields are strings or null. Lists return arrays. Create returns 201. Status request: `{ "status": "EXECUTED", "executed_price": "2550" }`; omit executed_price for SENT/DONE. Invalid input: 422; missing trade: 404; illegal transition: 409. FastAPI error detail may be string or validation array; frontend handles both.

Optional positions: sum BUY qty minus SELL qty for EXECUTED/DONE only, grouped by fund and instrument; these are net captured executions, not actual portfolio holdings without opening balances. Optional CSV uses a provisional header matching trade response fields, ISO dates and explicit currency; confirm final format with back office.

## 8. Independent acceptance tests
| Test | Expected result |
|---|---|
| JSE share: 100 × 2500 cents | ZAR 2500.00 |
| USD share: 10 × 150.25 | USD 1502.50 |
| Bond: nominal 100000 × 98.5 | 98500.00 in instrument currency |
| ALSI: 2 × 75000 × 10 | ZAR 1500000.00 notional |
| Close 100, trade 105 | No threshold warning |
| Close 100, trade 106 or 94 | Warning |
| Missing or zero close | Comparison unavailable; otherwise valid trade accepted |
| Unknown quote convention | Explicit error; no invented consideration |
| Missing side or broker | UI requires selection; API rejects |
| Zero/negative/nonfinite qty or price | API rejects |
| Unknown fund/broker/instrument | API rejects |
| DRAFT -> EXECUTED | Reject |
| SENT -> EXECUTED without price | Reject |
| Captured 2500 cents, executed 2550, qty 100 | Original retained; effective consideration ZAR 2550.00 |
| Restart backend | Trades remain persisted |
| Filter fund/date | Only matching trades shown |
| Historical trade | No future close used |

Use synthetic fixtures for unit tests only; demo must use imported market data. Verify at least one real trade through UI and API.


## 10. Questions to narrate to the desk
- Are bond trade prices clean or all-in? Where does accrued interest come from? Are closes on the same basis?
- Is the futures multiplier always 10? Does consideration mean notional, settlement value or margin?
- Is the price warning 5% or 10%, asset-specific, and advisory or blocking? What constitutes stale market data?
- Are partial executions, cancellations, corrections and multiple fills required?
- Are fractional shares allowed? What are nominal increments and rounding conventions?
- Should positions include opening balances, corporate actions and settlement dates?
- What is the required CSV schema, currency convention and business-day cutoff?
- Is SENT a manual confirmation or should the app send orders? Who may approve/mark DONE?
